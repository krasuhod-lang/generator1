# Техническое задание

## Исправление и усиление парсера сайтов, извлечения категорий клиентов и внутреннего бота-сканера

**Проект:** `krasuhod-lang/generator1`  
**Целевой исполнитель:** GPT-5.5 под контролем разработчика  
**Статус:** готово к реализации  
**Приоритет:** высокий  
**Область:** `audit` + `backend` + `frontend` + PostgreSQL + Docker Compose

---

## 1. Цель работы

Необходимо повысить устойчивость текущего парсера сайтов и превратить его из разового пакетного обработчика в надежный внутренний сервис, который умеет обходить сайты, собирать доказательства по нужным параметрам и формировать результат без падения всего задания при ошибке ответа ИИ.

Работа должна решить три основные проблемы:

1. Устранить ошибку вида `Ошибка ИИ: 'str' object has no attribute 'items'`, возникающую при отдельных форматах ответа DeepSeek/DSPy.
2. Обеспечить обязательное, однозначное и понятное заполнение полей **«Категории клиентов»** и **«С кем работает»**. Если на сайте нет подтверждающей информации, это должно быть явно указано, а не оставлено пустым.
3. Создать внутреннего бота-сканера, который будет автоматически обходить сайты, находить релевантные страницы, анализировать содержимое на предмет заданных параметров, сохранять доказательства и возвращать результат с прогрессом, повторными попытками и возможностью возобновления после перезапуска сервиса.

Текущая архитектура уже содержит два важных элемента, которые необходимо переиспользовать: Python audit-сервис с мини-краулером и LLM-извлечением, а также Node.js site crawler с BFS-обходом, проверкой robots.txt, sitemap, SSRF-защитой, ограничением глубины, количества страниц и параллелизма [1] [2]. Нельзя создавать второй полностью независимый механизм обхода без обоснования.

## 2. Текущее состояние и выявленные проблемы

### 2.1. Поток обработки

Сейчас интерфейс запускает задачу через `POST /api/parsers/start`. Node.js-контроллер сохраняет запись в `parser_tasks`, после чего запускает обработку URL в фоне. Для каждого сайта он вызывает внутренний endpoint audit-сервиса `/audit/parsers/extract`, передавая флаги извлечения контактов, описания, услуг и клиентов [3].

Python-модуль `audit/app/parsers.py` загружает главную страницу, выбирает внутренние ссылки, докачивает ограниченное число подстраниц, очищает HTML и передает объединенный текст в DSPy/DeepSeek. Для клиентских данных используются поля `client_segments` и `works_with` [4].

### 2.2. Ошибка `'str' object has no attribute 'items'`

Ошибка возникает внутри слоя обработки структурированного ответа DSPy, когда модель возвращает JSON не в ожидаемом виде: например, JSON-объект в виде строки, дважды сериализованную строку, fenced JSON, объект OpenAI-ответа с вложенным `choices`, либо смешанный текст с JSON-блоком. В текущем коде уже имеется попытка восстановить результат из `lm.history`, но она должна быть вынесена в самостоятельный нормализующий слой с полной валидацией типов и единым контрактом [4].

Критически важно, чтобы исключение из адаптера ответа ИИ не приводило к потере всего сайта. Если сырой ответ можно разобрать, результат должен считаться успешным или частично успешным. Если ответ разобрать нельзя, в отчете должна появиться понятная причина, а задача должна продолжить обработку остальных сайтов.

### 2.3. Пустые поля клиентов

В текущем контракте при отсутствии сведений используются `[]` для `client_segments` и пустая строка для `works_with`. Для API это допустимо, но для пользователя такой результат выглядит как ошибка или незаполненное поле. Кроме того, пустое значение не различает несколько разных ситуаций: на сайте действительно нет сведений, сайт недоступен, LLM не ответила, либо поле не запрашивалось.

Нужно разделить техническое состояние и пользовательское отображение. Внутри результата должны храниться статус поля, причина и доказательства. В Excel и интерфейсе поля должны быть непустыми и содержать явное сообщение.

### 2.4. Недостаточная надежность фоновых задач

Текущий `parsers.controller.js` запускает `processUrls()` после отправки HTTP-ответа. При рестарте Node-процесса выполнение может быть потеряно, несмотря на наличие записи в `parser_tasks`. Для внутреннего бота требуется очередь заданий, heartbeat, повторные попытки и восстановление зависших задач после рестарта.

### 2.5. Тестовая среда

Тесты audit-сервиса импортируют DSPy и Protego, поэтому должны запускаться внутри audit-контейнера либо после установки `audit/requirements.txt`. Локальный запуск без этих зависимостей не является корректной проверкой парсера [5].

## 3. Объем работ

Работу выполнить в четыре этапа.

| Этап | Содержание | Результат |
|---|---|---|
| A | Унификация и защита разбора ответа ИИ | Ошибка `str.items` устранена, добавлены типы, валидатор и регрессионные тесты |
| B | Надежное заполнение клиентских полей | Для каждого сайта формируются значение, статус, причина и доказательства |
| C | Внутренний бот-сканер | Долгоживущая очередь, обход сайтов, анализ параметров, сохранение прогресса |
| D | UI, экспорт и эксплуатация | Отображение статусов, доказательств, частичных ошибок, повторный запуск и мониторинг |

В рамках первой версии бот должен анализировать следующие параметры:

| Поле | Тип | Назначение |
|---|---|---|
| `contacts` | строка или структурированный объект | Телефоны, e-mail, адреса, мессенджеры |
| `about` | строка | Описание компании и ее специализации |
| `services` | массив строк | Услуги или решения, явно указанные на сайте |
| `focus` | строка | Основной коммерческий фокус и специализация |
| `client_segments` | массив строк | Обобщенные категории клиентов, без названий брендов |
| `works_with` | строка | Формат B2B/B2C/B2G и тип клиентов |
| `evidence` | массив объектов | URL, цитата, тип сигнала и поле, которое подтверждается |
| `field_status` | объект | Состояние извлечения каждого поля |

## 4. Требования к исправлению ошибки ответа ИИ

### 4.1. Единый нормализатор

Создать отдельный модуль, например `audit/app/ai_response_normalizer.py`, не смешивая разбор ответа ИИ с бизнес-логикой краулера. Модуль должен принимать любое значение типа `Any` и возвращать единый результат:

```python
{
    "fields": {
        "contacts_summary": "...",
        "about_summary": "...",
        "services_list": ["..."],
        "main_focus": "...",
        "client_segments": ["..."],
        "works_with": "..."
    },
    "raw_text": "...",
    "source_type": "dspy_prediction|json|openai_response|labeled_text|history",
    "warnings": [],
    "parse_status": "ok|partial|invalid"
}
```

Нормализатор обязан корректно обрабатывать:

| Входной формат | Ожидаемое поведение |
|---|---|
| Python `dict` | Нормализовать ключи и значения без вызова `.items()` на строке |
| Строка с JSON-объектом | Распарсить объект |
| Дважды сериализованный JSON | Сначала распарсить строку, затем внутреннюю JSON-строку |
| JSON в блоке `````json ... ````` | Удалить markdown-обертку и распарсить содержимое |
| OpenAI-ответ с `choices[].message.content` | Извлечь контент и передать в JSON/labeled parser |
| DSPy Prediction | Попробовать `toDict`, `to_dict`, `model_dump`, `dict`, затем атрибуты полей |
| `lm.history` | Рекурсивно искать последний распознаваемый ответ |
| Обычный labeled text | Распознать поля по русским и английским меткам |
| `None`, число, неизвестный объект | Вернуть `parse_status=invalid`, не выбрасывать необработанное исключение |

Запрещается вызывать `.items()` до проверки `isinstance(value, dict)`. Любое приведение к строке должно происходить только после проверки допустимого типа.

### 4.2. Валидация результата

После нормализации добавить валидатор результата. Для Python использовать Pydantic-модель либо эквивалентную строгую функцию валидации. Валидатор должен:

- приводить `services_list` и `client_segments` к массиву строк;
- приводить `contacts_summary`, `about_summary`, `main_focus` и `works_with` к строке;
- удалять пустые элементы, markdown-маркеры и дубликаты;
- не принимать словари внутри массива без явного преобразования в строку;
- сохранять частичный результат, если заполнены хотя бы некоторые поля;
- добавлять предупреждение, если модель вернула неожиданный тип;
- запрещать конкретные названия брендов в `client_segments`, если они не являются категорией клиента;
- не считать общие слова вроде «клиенты», «люди», «бизнес» достаточным доказательством категории.

### 4.3. Стратегия вызова LLM

Основной вызов можно оставить на DSPy, но необходимо исключить зависимость бизнес-логики от того, сможет ли адаптер DSPy сам распарсить ответ. Реализовать следующую последовательность:

1. Вызвать LLM с требованием вернуть один JSON-объект.
2. Получить prediction и передать его в единый нормализатор.
3. При исключении DSPy попытаться разобрать сырой ответ из `lm.history`.
4. Если история недоступна или не распознается, выполнить один контролируемый fallback-вызов через существующий OpenAI-compatible endpoint либо вернуть `parse_status=invalid`.
5. При наличии частичного результата применить его к сайту и сохранить предупреждение.
6. Не делать бесконечные повторы. Рекомендуемый лимит: основной вызов плюс один fallback и не более двух сетевых retry для временных ошибок.

В логах фиксировать `task_id`, URL, модель, попытку, тип входного ответа, `parse_status`, длительность и код ошибки. Не записывать API-ключ и полный сырой ответ в обычный лог. Сырой ответ разрешается сохранять только в отладочный storage с ограничением размера и маскированием секретов.

### 4.4. Статусы обработки ИИ

Использовать машинные коды, а не сравнение длинных русских строк:

| Код | Значение |
|---|---|
| `ok` | Ответ разобран, результат валиден |
| `partial` | Часть полей восстановлена, часть отсутствует или невалидна |
| `not_found` | Сайт доступен, но подтверждающих сведений нет |
| `llm_error` | Сайт доступен, но LLM не ответила или ответ не удалось разобрать |
| `fetch_error` | Сайт не удалось получить |
| `blocked_by_robots` | Обход запрещен robots.txt |
| `cancelled` | Задание остановлено пользователем |

Поле `status` сайта должно содержать общий статус, а `field_status` — статус каждого поля отдельно.

## 5. Требования к полям «Категории клиентов» и «С кем работает»

### 5.1. Правило доказательности

LLM должна формировать категории клиентов только при наличии на сайте подтверждающих сигналов. Источниками сигнала считаются:

- страницы «Клиенты», «Кейсы», «Портфолио», «Проекты», «Отрасли», «Решения», «Для кого» и аналогичные;
- страницы конкретных услуг, если в них явно назван тип заказчика;
- формулировки «работаем с…», «для…», «помогаем…», «наши клиенты…»;
- описания кейсов, задач и болей конкретного сегмента;
- CTA и формы, в которых явно указан тип клиента;
- структурированные данные и текстовые блоки, если они подтверждают категорию.

Названия отдельных компаний, логотипы и бренды необходимо обобщать до категории: например, «стоматологии», «производственные компании», «государственные заказчики», «частные клиенты». Нельзя делать вывод только из названия услуги или общей тематики сайта.

### 5.2. Обязательный пользовательский результат

При включенном извлечении клиентов оба поля всегда должны быть непустыми.

Если подтверждающая информация найдена:

```json
{
  "client_segments": [
    "стоматологии — привлечение пациентов и маркетинг",
    "медицинские центры — продвижение услуг"
  ],
  "works_with": "B2B: медицинские организации",
  "field_status": {
    "client_segments": "found",
    "works_with": "found"
  }
}
```

Если сайт доступен, но сведений нет:

```json
{
  "client_segments": [
    "Не определено — на сайте нет явных данных о категориях клиентов"
  ],
  "works_with": "Не определено — на сайте нет явных указаний, с кем работает компания",
  "field_status": {
    "client_segments": "not_found",
    "works_with": "not_found"
  },
  "evidence": []
}
```

Если сайт не удалось получить:

```json
{
  "client_segments": [
    "Не определено — сайт недоступен или не удалось получить его содержимое"
  ],
  "works_with": "Не определено — анализ невозможен из-за ошибки доступа к сайту",
  "field_status": {
    "client_segments": "fetch_error",
    "works_with": "fetch_error"
  }
}
```

Если сайт получен, но LLM не обработала ответ:

```json
{
  "client_segments": [
    "Не удалось определить — ошибка анализа ИИ"
  ],
  "works_with": "Не удалось определить — ошибка анализа ИИ",
  "field_status": {
    "client_segments": "llm_error",
    "works_with": "llm_error"
  }
}
```

Эти сообщения являются обязательным пользовательским fallback и не должны смешиваться с реальными категориями. Для аналитики необходимо хранить отдельные машинные статусы, чтобы sentinel-значения не попадали в статистику как настоящие сегменты.

### 5.3. Доказательства

Для каждого найденного сегмента сохранить минимум один объект доказательства:

```json
{
  "field": "client_segments",
  "url": "https://example.com/clients",
  "quote": "Работаем со стоматологиями и медицинскими центрами",
  "signal_type": "explicit_phrase|case|service_page|cta|schema|about",
  "confidence": 0.97
}
```

Цитата должна быть короткой, достаточной для проверки вывода и взятой из реально загруженного текста. Если доказательства нет, значение не может считаться найденной категорией.

### 5.4. Excel и API

Существующие колонки Excel сохранить для обратной совместимости:

- `Категории клиентов` — каждый элемент с новой строки;
- `С кем работает` — одна строка;
- `Статус парсинга` — общий статус.

Добавить колонки:

- `Статус категорий клиентов`;
- `Статус поля «С кем работает»`;
- `Доказательства клиентов`;
- `Предупреждения`;
- `Количество просканированных страниц`.

В API возвращать как legacy-поля, так и структурированный объект `analysis` либо `field_status` и `evidence`, чтобы существующий frontend не сломался.

## 6. Требования к внутреннему боту-сканеру

### 6.1. Назначение

Внутренний бот — это серверный worker, который принимает список сайтов или одну задачу на сайт, обходит разрешенные страницы, собирает текстовые сигналы, запускает анализ нужных параметров, сохраняет промежуточный результат и формирует итоговый отчет.

Бот не должен быть чат-ботом, который отвечает только в рамках HTTP-запроса. Он должен работать как автономный обработчик очереди и не зависеть от того, открыт ли браузер пользователя.

### 6.2. Предлагаемая архитектура

Рекомендуемый вариант — использовать существующий Node.js backend как диспетчер и durable worker, существующий audit Python-сервис как слой загрузки/очистки/LLM-анализа, PostgreSQL как источник истины и текущие механизмы site crawler для безопасного обхода [2] [3].

Поток обработки:

```text
Пользователь / API
        |
        v
Создание parser_scan_task
        |
        v
PostgreSQL-очередь
        |
        v
Worker: claim -> crawl -> collect evidence -> analyze -> validate -> persist
        |                         |
        |                         v
        |                  audit service / LLM
        v
Прогресс, повтор, отмена, возобновление
        |
        v
API + Excel/JSON + frontend
```

Для обхода необходимо переиспользовать `siteCrawler/crawler.js`, `robotsClient.js`, `ssrfGuard.js` и `urlNormalizer.js`, а для LLM-извлечения — общий нормализатор из раздела 4. Если текущий Node crawler не сохраняет достаточно текста для анализа, добавить отдельный режим `analysis`, который сохраняет очищенный текст временно либо передает его в audit-сервис без постоянного хранения сырого HTML.

### 6.3. Очередь и возобновление

Создать отдельные таблицы `parser_scan_tasks` и `parser_scan_items` либо расширить `parser_tasks`, если это не ухудшает обратную совместимость. Предпочтительно создать новые сущности, потому что текущий `parser_tasks` хранит только общий JSON-результат и не содержит достаточного состояния для возобновления по отдельным URL.

Минимальная структура:

```sql
parser_scan_tasks
- id UUID PRIMARY KEY
- user_id UUID NULL
- project_id UUID NULL
- status TEXT -- queued|running|paused|done|partial|error|cancelled
- options JSONB
- total INT
- processed INT
- succeeded INT
- failed INT
- created_at TIMESTAMPTZ
- started_at TIMESTAMPTZ NULL
- finished_at TIMESTAMPTZ NULL
- heartbeat_at TIMESTAMPTZ NULL
- worker_id TEXT NULL
- error TEXT NULL

parser_scan_items
- id UUID PRIMARY KEY
- task_id UUID REFERENCES parser_scan_tasks(id) ON DELETE CASCADE
- input_url TEXT
- normalized_url TEXT
- status TEXT -- queued|running|done|partial|error|cancelled
- attempts INT DEFAULT 0
- next_attempt_at TIMESTAMPTZ NULL
- started_at TIMESTAMPTZ NULL
- finished_at TIMESTAMPTZ NULL
- result JSONB NULL
- field_status JSONB NULL
- evidence JSONB NULL
- stats JSONB NULL
- error_code TEXT NULL
- error_message TEXT NULL
- content_hash TEXT NULL
- UNIQUE(task_id, normalized_url)
```

Worker должен забирать задания атомарно через транзакцию и `FOR UPDATE SKIP LOCKED`. Зависшие элементы, у которых `status=running` и `heartbeat_at` старше заданного TTL, переводить обратно в `queued` с увеличением `attempts`. После рестарта worker автоматически подхватывает незавершенные элементы.

### 6.4. Настройки сканирования

Добавить серверные настройки с безопасными пределами:

| Параметр | Значение по умолчанию | Ограничение |
|---|---:|---:|
| `max_pages_per_site` | 100 | 1–1000 |
| `max_depth` | 5 | 0–10 |
| `concurrency` | 4 | 1–16 |
| `request_timeout_ms` | 15000 | 1000–60000 |
| `max_response_bytes` | 2 MB | 64 KB–20 MB |
| `inter_request_ms` | 250 | 0–10000 |
| `respect_robots` | `true` | нельзя отключать для публичного режима без admin-флага |
| `use_sitemap` | `true` | boolean |
| `max_llm_calls_per_site` | 2 | 1–3 |
| `retry_limit` | 2 | 0–5 |

Приоритетно обходить страницы и ссылки с признаками `clients`, `cases`, `portfolio`, `projects`, `reviews`, `industries`, `solutions`, `for`, `для`, `кому`, `отрасл`, `партнер`, `услуги`, `контакты`, `о компании`. При этом не ограничиваться только такими URL: если релевантная информация находится на обычной внутренней странице, она также должна быть доступна ограниченному BFS-обходу.

### 6.5. Безопасность

Обязательно сохранить и покрыть тестами:

- запрет SSRF к localhost, loopback, private и link-local адресам;
- проверку каждого redirect и каждого нового host;
- ограничение домена и поддоменов;
- respect robots.txt;
- запрет обхода бинарных файлов, архивов и не-HTML ресурсов;
- лимит размера ответа и глубины обхода;
- таймауты и ограничение параллелизма;
- отсутствие API-ключей в логах и Excel;
- дедупликацию URL после нормализации query, hash и trailing slash по существующим правилам проекта.

### 6.6. Идемпотентность и кэш

Результат одного и того же URL не должен дублироваться в рамках одного задания. Для повторных запусков использовать `content_hash` очищенного текста и версию prompt/schema. Ключ кэша должен учитывать URL, выбранные поля, версию анализатора, версию prompt и модель. После изменения prompt или схемы старый результат нельзя безусловно выдавать как новый.

## 10. План тестирования

### 10.1. Unit-тесты нормализатора

Добавить тесты для следующих входов:

1. обычный Python dictionary;
2. JSON-объект в строке;
3. дважды сериализованный JSON;
4. fenced JSON;
5. OpenAI-compatible `choices[].message.content`;
6. DSPy prediction с атрибутами;
7. `lm.history` с `outputs` как строкой;
8. labeled text на русском;
9. `client_segments` как строка, массив, tuple, `None`, словарь;
10. неизвестный тип без метода `items`;
11. пустой и поврежденный ответ;
12. дубликаты и пустые элементы;
13. ответ с частично заполненными полями;
14. ответ с sentinel-значениями;
15. попытка передать конкретный бренд вместо категории.

Отдельный регрессионный тест должен воспроизводить точную ошибку:

```python
raise AttributeError("'str' object has no attribute 'items'")
```

Тест должен подтверждать, что после ошибки результат восстанавливается из сырого ответа или корректно превращается в `llm_error`, не ломая задачу.

### 10.2. Integration-тесты audit

Использовать mock fetcher и mock LLM, не делать реальные сетевые вызовы. Подготовить HTML-фикстуры:

| Фикстура | Ожидание |
|---|---|
| Главная + `/clients` с явными отраслями | Категории найдены, есть доказательства |
| Главная без клиентских сигналов | `not_found` и непустые sentinel-поля |
| Недоступный сайт | `fetch_error`, задача не падает глобально |
| Сайт с `/cases` на втором уровне | Кейс найден ограниченным BFS |
| Страница с JSON-LD и обычным текстом | Сигналы объединены, приоритет у подтвержденного текста |
| Модель вернула JSON как строку | Результат успешно восстановлен |
| Модель вернула поврежденный JSON | `llm_error` либо `partial`, без исключения наружу |

### 10.3. Integration-тесты Node.js worker

Проверить создание задания, атомарный claim, heartbeat, возврат зависшего задания в очередь, cancel, retry failed items, уникальность URL и корректное обновление счетчиков `total`, `processed`, `succeeded`, `failed`.

Отдельно проверить перезапуск: создать item со статусом `running` и устаревшим heartbeat, запустить worker и убедиться, что item снова обрабатывается.

### 10.4. Security-тесты

Проверить SSRF на `127.0.0.1`, `localhost`, private IPv4, link-local IPv4, IPv6 loopback, redirect на запрещенный адрес, внешний домен в sitemap и ссылку на бинарный файл. Проверить, что robots.txt блокирует страницу и что лимиты не обходятся через sitemap или огромное меню.

### 10.5. Нагрузочный smoke-test

На 50–100 URL проверить, что один неработающий сайт не блокирует остальные, память не растет бесконтрольно, количество LLM-вызовов ограничено, прогресс обновляется, а итоговый Excel формируется даже при смешанном результате `done/partial/error`.

## 13. Варианты реализации внутреннего бота

| Подход | Плюсы | Минусы | Рекомендация |
|---|---|---|---|
| Durable worker на Node.js + PostgreSQL + существующий audit | Минимум новых сервисов, использует текущий стек, задания переживают рестарт, легко связать с существующим API | Нужно добавить миграции, heartbeat и worker loop | **Основной вариант** |

## 15. Обязательное требование: задачи не должны слетать при обновлении сервера

### 15.1. Результат анализа текущей реализации

В текущем проекте обнаружены независимые причины, из-за которых задачи могут потеряться или навсегда остаться в состоянии выполнения.

| Компонент | Текущая проблема | Последствие после рестарта |
|---|---|---|
| `parser_tasks` | `processUrls()` запускается из HTTP-контроллера через fire-and-forget вызов; промежуточные результаты хранятся в памяти и сохраняются только после всего batch | Задача остается `running`, результаты и Excel теряются |
| `site_crawl_tasks` | `crawler.runCrawl()` запускается через `setImmediate`; нет startup-recovery worker для `queued/running` | После рестарта задача может остаться без процесса-владельца |
| Python audit `/audit/start` | Выполнение живет в `asyncio.create_task()` внутри одного процесса | Redis может сохранить статус, но не восстановить coroutine после рестарта |
| Audit store | При проблеме Redis происходит in-memory fallback | При перезапуске теряются рабочие snapshots |
| Backend shutdown | Нет общего SIGTERM/SIGINT shutdown для HTTP-сервера и фоновых schedulers | Обновление может оборвать работу между критическими операциями |
| Parser progress | Результат сайта не сохраняется после каждого item | При сбое теряется уже выполненная работа |

В репозитории уже есть эталон надежного выполнения: BullMQ worker основного пайплайна использует checkpoint-aware auto-resume, stalled-job detection и graceful shutdown по SIGTERM/SIGINT [7]. Этот подход необходимо применить к parser и site-crawler worker.

### 15.2. Требуемая гарантия надежности

Под «бесперебойной работой» понимать следующие гарантии:

1. Обновление или рестарт сервера не приводит к потере задания, URL, обработанных страниц и сохраненного результата.
2. После запуска новой версии незавершенные задачи автоматически продолжаются с последней подтвержденной точки.
3. Во время короткого перезапуска допускается пауза, но пользователь не создает задачу заново.
4. Один item может быть выполнен повторно после аварии, но идемпотентная запись не создает дубликат результата.
5. Задание не находится бесконечно в `queued` или `running` без heartbeat, recovery или финального статуса.
6. При окончательной ошибке сохраняются `partial/error`, причина, счетчики и возможность повторить только неуспешные items.

Полное отсутствие паузы требует нескольких worker-реплик и rolling/blue-green deployment. Базовая реализация обязана обеспечить непотерю задач и автоматическое возобновление при временном перезапуске контейнера.

### 15.3. Разделение API и выполнения

Нельзя выполнять длительный parser, crawler или audit непосредственно в процессе HTTP-запроса и нельзя считать `setImmediate()` надежной очередью.

| Роль | Обязанность |
|---|---|
| API backend | Валидирует запрос, создает записи заданий/items и ставит job в очередь |
| PostgreSQL | Хранит источник истины: статусы, lease, checkpoint, результаты и ошибки |
| Redis/BullMQ | Доставляет job worker-у, обнаруживает stalled jobs, retry/backoff |
| Parser/crawler worker | Обрабатывает items, регулярно сохраняет checkpoint и heartbeat |
| Audit service | Выполняет fetch/clean/LLM-анализ по запросу worker-а, но не владеет всей жизнью задания |
| Recovery/watchdog | Возвращает зависшие items в очередь и восстанавливает рассинхронизацию |

В репозитории уже используется отдельный BullMQ worker-контейнер [10]. Для parser и crawler создать отдельные очереди, например `parser-scans` и `site-crawls`, чтобы тяжелые операции не блокировали генерацию контента.

### 15.4. Очередь и транзакционная постановка

Создать записи задания и items в PostgreSQL до запуска обработки. Предпочтительно использовать **transactional outbox**: в одной транзакции создать task, items и outbox-событие; publisher с `FOR UPDATE SKIP LOCKED` публикует job в BullMQ и отмечает событие опубликованным. При сбое publisher повторяет отправку.

Допустим упрощенный reconciler, который каждые 30–60 секунд ищет `queued` items без активной BullMQ job и повторно ставит их в очередь. Запись только в памяти запрещена. Нельзя считать задачу надежно поставленной, если сохранен только ответ `queue.add()`, но не состояние PostgreSQL.

### 15.5. Lease, heartbeat и checkpoint

Для `parser_scan_item`, `site_crawl_task` и долгого audit item добавить:

```text
status: queued | running | retry_wait | done | partial | error | cancelled
attempts: integer
worker_id: text nullable
lease_token: uuid nullable
lease_until: timestamptz nullable
heartbeat_at: timestamptz nullable
checkpoint: jsonb nullable
last_error_code: text nullable
last_error_message: text nullable
```

Worker получает уникальный `lease_token`. Все записи выполнять с условием `WHERE id = $1 AND lease_token = $2`, чтобы старый worker после истечения lease не мог перезаписать результат нового worker-а.

Heartbeat обновлять каждые 10–15 секунд, lease продлевать примерно на 60 секунд. Для parser сохранять checkpoint после каждого URL. Для crawler — после каждой страницы либо батча максимум из 10 страниц. Checkpoint должен включать последний URL, глубину, посещенные URL/очередь, настройки обхода, версию worker и хеш входного задания.

### 15.6. Startup recovery

При старте backend/worker выполнить recovery под PostgreSQL advisory lock:

1. Дождаться healthcheck PostgreSQL и Redis.
2. Найти `running` items с истекшим `lease_until` или устаревшим heartbeat.
3. Перевести их в `retry_wait`/`queued`, увеличить `attempts`, записать `worker_restarted`.
4. Найти `queued` items без активной BullMQ job и восстановить публикацию через outbox/reconciler.
5. Не трогать `done`, `cancelled`, `partial` и финальный `error`, если пользователь не запросил retry.
6. Запустить worker и watchdog только после успешной инициализации схемы.

Для audit `/audit/start` Node worker должен владеть родительским заданием и повторять запрос к audit-сервису после временной потери Python-контейнера. Если audit остается асинхронным, его `queued/running` задачи должны иметь durable queue/lease и startup recovery. Redis snapshot сам по себе не восстанавливает `asyncio.create_task()` [8] [9].

### 15.7. Watchdog и зависшие задачи

Добавить `taskRecoveryScheduler` либо расширить существующий watchdog-паттерн для зависших project analyses [11]. Минимальные интервалы:

| Проверка | Интервал | Действие |
|---|---:|---|
| Heartbeat | 10–15 с | Обновление lease активного item |
| Recovery expired leases | 30 с | Возврат просроченных `running` в очередь |
| Queue reconciler | 30–60 с | Поиск queued items без BullMQ job |
| Stale queued alert | 1–5 мин | Предупреждение о голодании очереди |
| Maximum execution timeout | По типу задачи | Retry/partial/error |

Watchdog сначала должен вернуть item в очередь, а не сразу ставить ошибку. В `error` переводить после исчерпания attempts или абсолютного timeout. Логировать `task_id`, `item_id`, `worker_id`, старый/новый статус, причину, attempt и длительность. Добавить метрики `queue_depth`, `oldest_queued_age`, `active_jobs`, `stale_reclaimed_total`, `retry_total`, `task_completed_total`, `task_failed_total`.

### 15.8. Graceful shutdown и Docker update

Для parser worker, crawler worker и audit worker реализовать SIGTERM/SIGINT по аналогии с текущим BullMQ worker [7]: перестать брать новые jobs, сохранить checkpoint, вернуть текущий item в очередь либо продлить lease, закрыть очередь и DB-транзакции, затем завершить процесс.

Для API backend добавить graceful shutdown: прекратить прием новых длительных операций, закрыть HTTP server, остановить schedulers/watchdog и закрыть DB/Redis connections. Длительная обработка не должна удерживаться API-процессом.

В `docker-compose.yml` задать `stop_grace_period` для всех worker-контейнеров, healthcheck для backend/worker и зависимости от PostgreSQL/Redis. Обновление проводить в следующем порядке:

```text
1. Применить backward-compatible миграции под advisory lock.
2. Запустить новую версию worker рядом со старой либо дождаться graceful drain.
3. Проверить healthcheck и наличие worker-а.
4. Перезапустить API backend.
5. Запустить recovery/reconciler.
6. Проверить отсутствие running items без heartbeat.
```

Миграции сначала должны быть совместимы со старой версией приложения. Нельзя удалять колонки, пока старый worker еще может выполнять jobs.

### 15.9. Обязательные тесты рестарта

| Сценарий | Проверка |
|---|---|
| SIGTERM parser/crawler worker | item продолжает работу, результат не теряется |
| SIGKILL worker | истекший lease автоматически возвращается в очередь |
| Restart backend до публикации job | outbox/reconciler публикует job повторно |
| Restart audit во время LLM | Node worker выполняет retry, задача не зависает |
| Restart Redis | PostgreSQL-статус сохраняется, очередь восстанавливается |
| Restart PostgreSQL | worker делает backoff и продолжает после восстановления |
| `docker compose up -d --build` | незавершенные items не теряются |
| Duplicate BullMQ job | нет дубля благодаря lease и idempotent upsert |
| Два worker-а одновременно | только владелец lease может сохранить результат |
| Медленный/недоступный сайт | timeout/retry не блокирует остальные сайты |
| Старый queued item | watchdog восстанавливает его или выдает понятный alert |

Smoke-test проверяет не только финальный статус, но и наличие всех items, checkpoint, attempts и отсутствие `running` без свежего heartbeat.

### 15.10. Дополнительные критерии приемки

1. После SIGTERM, SIGKILL и пересоздания контейнера незавершенная задача автоматически продолжается.
2. Ни один item не находится в `running` дольше lease TTL без recovery.
3. Результат каждого завершенного сайта сохраняется независимо от завершения batch.
4. API-процесс не является единственным местом хранения очереди или выполнения длительной задачи.
5. Задание, созданное до обновления, обрабатывается новой версией без ручного переноса.
6. Publisher/reconciler устраняет рассинхронизацию PostgreSQL и BullMQ.
7. Worker имеет graceful shutdown и собственный Docker `stop_grace_period`.
8. В мониторинге видны размер очереди, возраст старейшей задачи, retry, recovery и ошибки worker-а.
9. В PR приложен протокол теста с перезапуском контейнеров и перечнем восстановленных задач.
